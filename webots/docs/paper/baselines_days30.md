## 3. 시드와 오류 설정

`tools/make_day_split.py` 맨 위의 변수다. 베이스라인 비교에서는 바꾸지 않는다.

| 변수 | 값 | 뜻 |
|---|---|---|
| `TRAIN_SEEDS` | [42] | 학습 날짜마다 시드 하나. 입고 트럭과 오류 위치를 정한다 |
| `TEST_SEEDS` | [54] | 시험 날짜마다 시드 하나 |
| `LEVELS` | [0.03, 0.065, 0.10] | 초기 기록 오류 수준. 재고가 있는 칸 중 오류 칸의 비율이다. 학습 날짜는 날짜순으로 돌아가며 한 수준씩(수준마다 9일), 시험 날짜는 세 수준 모두 받는다 |
| `MIX` | mixed | Ghost : Hidden = 1 : 1 |
| `SLIP_P` | 0.01 | 에피소드 중 기록 오류. 완료된 적치·재배치 중 이 비율이 다른 칸에 기록된다 |
| `err_seed` | 시드 + 1000 | 초기 오류 추첨 |

- **로봇:** 8대 (`gen_world.py --plain` 기본 배치).
- **에피소드:** 3600초.
- **학습 중 시드:** `tools/train_assign.py --batch 0`은 학습 시나리오의 `seed`를 0으로 덮어쓴다. 입고와 초기 오류는 파일에 고정되어 있으므로 바뀌는 것은 기록 slip 추첨과 스케줄러 난수뿐이다. 새 기법도 같은 방식으로 학습하려면 같은 함수(`train_assign.episode`)로 에피소드를 돌리면 된다. 다르게 하면 보고서에 적는다.

## 4. 베이스라인

세 베이스라인 모두 확인 작업(VERIFY) 정책은 `VERIFY_POLICY=event`이다. 예외 처리(SHORT_PICK, DESTINATION_OCCUPIED 대응)는 `lib/sched_verify.py`의 것을 쓴다. 차이는 로봇–작업 배정 방식뿐이다.

| 이름 | 실행 설정 | 배정 방식 |
|---|---|---|
| 팀 WES | `WES_SCHEDULER=sched_verify` | 팀의 규칙 기반 배정 (`lib/sched_verify.py`) |
| 헝가리안 | `WES_SCHEDULER=sched_hungarian` | 매 순간 놀고 있는 로봇과 시작 가능한 작업(오래된 순 30개)을, 로봇에서 작업까지 거리의 합이 최소가 되게 짝짓는다 (`lib/sched_hungarian.py`, scipy `linear_sum_assignment`) |
| CEM | `WES_SCHEDULER=sched_learned ASSIGN_WEIGHTS=models/assign_weights_days30_cem_r{0,1,2}.json` | 특징 11개의 선형 점수로 배정한다. 가중치는 경량 시뮬레이터에서 CEM으로 학습했다 (`lib/sched_learned.py`) |

**CEM 학습 명령.** 가중치는 커밋되어 있어서 다시 학습할 필요는 없다. 아래는 재현용이다.

```bash
for r in 0 1 2; do
  python tools/train_assign.py --train "logs/days30/train/*.json" --test "logs/days30/test/*.json" --test-seeds 54 \
    --robots 8 --batch 0 --missed-w 100 --rng $r --workers 6 \
    --out models/assign_weights_days30_cem_r$r.json --report logs/train_days30_cem_r${r}_report.json
done
```

- 비용: `mix` = 0.5 × 주문 리드 + 0.5 × 단위 리드 + 100 × 마감 놓침.
- 탐색: CEM 15회 반복, 후보 24개, 엘리트 6개, 초기 표준편차 1.0.
- 최종 가중치: 마지막 반복의 평균이다(최고 후보가 아님).
- 한 번 학습에 경량 에피소드 15 × 25 × 27 = 10,125개(팀 WES 참조 포함)가 든다. 작업자 6개로 약 2시간이다.
- `--test`는 학습이 끝난 뒤 표를 만들 때만 쓴다.

**베이스라인이 아닌 것.** `models/assign_weights_fault_*`는 지금은 없앤 오류 환경에서 학습한 가중치라 비교에 쓰지 않는다.

## 5. 새 기법 규칙

### 5.1 끼워 넣는 방법

`lib/<name>.py`에 스케줄러 모듈을 만든다. 인터페이스는 `lib/wes_runner.py` 맨 위 설명과 `docs/wms.md`에 있다.

```python
class Scheduler:
    name = "my_policy"                       # 로그 폴더 이름에 들어간다
    def __init__(self, cfg): ...             # 시나리오 dict
    def plan(self, state): return [...]      # 매 스텝 결정 목록
    def on_event(self, ev, state): return [] # 선택
```

**학습한 모델 파일은 환경 변수 `ASSIGN_WEIGHTS`로 받고, `name`에 그 파일 이름을 넣는다.** 예: `self.name = "ppo-" + Path(os.environ["ASSIGN_WEIGHTS"]).stem`. 이유는 두 가지다.
- 로그 폴더 이름이 `name`으로 정해진다. r0–r2가 같은 이름이면 같은 폴더에 덮어쓴다.
- 비교 도구는 정책 이름을 `ASSIGN_WEIGHTS`의 파일 이름에서 읽는다(`run_env.json`에 기록됨). `sched_learned`가 이미 이렇게 한다.

배정만 바꾸는 기법이면 헝가리안처럼 `sched_learned.Scheduler`를 상속하고 `plan`만 바꾼다. 그래야 VERIFY와 예외 처리가 베이스라인과 같아진다. VERIFY나 예외 처리까지 바꾸면 결과에 그 사실을 적는다.

### 5.2 정책이 보면 안 되는 것

정책은 `state`(WMS 기록 기반 `WMSView`)로만 창고를 본다. 아래 정보는 읽지 않는다.

- `cfg["initial_record_errors"]`, `cfg["initial_record_errors_meta"]`, `cfg["record_slip_p"]`: 어느 칸이 틀렸는지, 얼마나 틀리는지에 대한 정답
- WMS 내부의 `record_slips`, 실행 폴더의 `truth.jsonl`
- 시험 시나리오 파일과 시험 날짜의 주문 파일

### 5.3 학습: r0, r1, r2

- 학습 데이터, 설정, 계산량은 모두 같게 두고 **난수 시드만 0, 1, 2로 바꿔 독립 학습 3회**를 돌린다. 각각 r0, r1, r2라 부른다.
- 가중치나 모델 파일 이름은 `<기법>_r0`, `<기법>_r1`, `<기법>_r2`로 한다. 그러면 비교 도구의 `--group`으로 묶을 수 있다.
- **셋 다 Webots에서 평가하고 셋 다 보고한다.** 대표값은 시나리오마다 세 결과를 평균한 값이다.
  - 가장 좋은 하나만 고르면 안 된다. CEM에서 세 번의 차이는 팀 WES 대비 −20초, −4초, −15초로 컸다.
  - 실패한 학습도 빼지 않는다.
- 최종 모델을 고르는 규칙(마지막 반복, 학습 데이터 안 검증 최고 등)은 학습 전에 정하고 적는다. 시험 결과를 보고 고르지 않는다.
- 학습에 쓴 에피소드 수와 걸린 시간을 적는다. CEM은 1회 10,125 에피소드, 약 2시간이었다.

## 6. 평가

### 6.1 Webots 실행

```bash
bash tools/webots_days30.sh mod:<module>:models/<기법>_r0.<ext> mod:<module>:models/<기법>_r1.<ext> mod:<module>:models/<기법>_r2.<ext>
```

- 정책 지정 방식:
  - `S`: 팀 WES
  - `H`: 헝가리안
  - `days30_cem_r0`처럼 가중치 이름: `sched_learned`
  - `mod:<module>`: 학습 파일 없는 새 스케줄러
  - `mod:<module>:<모델 파일>`: 새 스케줄러 + `ASSIGN_WEIGHTS=<모델 파일>`
- 한 시나리오의 정책들은 동시에 돈다. 4개 이하로 묶는다.
- 시나리오 9개에 1–4시간 걸린다. 무거운 날짜일수록 오래 걸린다.
- Webots 경로는 `WEBOTS` 환경 변수로 바꾼다.
- 실행 폴더는 `logs/<date>_wms-<name>-event_seed54_iri<level>-mixed_d30_batch/`이다. 실행 폴더에는 `scenario.json`과 `run_env.json`이 함께 남는다.
- `ASSIGN_WEIGHTS` 말고 다른 환경 변수가 필요하면, 그 변수 이름을 supervisor의 `run_env.json` 목록(`controllers/supervisor/supervisor.py`)에도 넣는다. 그래야 실행 폴더만 보고 설정을 추적할 수 있다.

**베이스라인도 같은 코드로 다시 돌린다.** `lib/`, `controllers/`, `worlds/`를 바꿨거나 다른 PC에서 돌린다면 베이스라인을 먼저 다시 돌린다. 쌍 비교는 같은 코드, 같은 PC에서 나온 실행끼리만 한다.

```bash
bash tools/webots_days30.sh S H days30_cem_r0 days30_cem_r1
bash tools/webots_days30.sh days30_cem_r2
```

### 6.2 지표

`tools/validate_lite.py`의 `events_metrics`가 실행 폴더의 `events.jsonl`에서 계산한다.

| 지표 | 정의 |
|---|---|
| **주문 리드 (주)** | 주문이 들어온 시각(`ORDER_RELEASED`)부터 그 주문의 마지막 유닛이 출고 트럭으로 떠난 시각(`OUTBOUND_DEPARTED`)까지. 끝나지 않은 주문은 에피소드 끝(3600초)을 쓴다. 모든 주문의 평균 |
| p90 | 위 주문 리드의 90번째 백분위 |
| 단위 리드 | 같은 계산을 유닛 하나 단위로 |
| 출고 | 떠난 유닛 수 |
| SHORT_PICK, DEST_OCC | 기록 오류로 생긴 예외 건수 |
| 가동률 | 운반 로봇의 평균 바쁜 시간 비율 |

`summary.json`의 `mean_order_lead_s`는 끝난 주문만 평균하므로 주 지표로 쓰지 않는다.

### 6.3 비교와 보고

```bash
python tools/compare_days30.py --group days30_cem=days30_cem_r --group <기법>=<기법>_r --out logs/compare_<기법>.md
```

출력:
- 정책마다 지표 평균
- 팀 WES 대비, 헝가리안 대비 주문 리드 쌍 차이 [95% CI] (이긴 시나리오 수)
- `--group` 평균 행
- 시나리오별 주문 리드

보고에 넣을 것:
1. 전체 표. 새 기법 r0, r1, r2와 평균, 베이스라인 셋(CEM은 r0–r2와 평균)
2. 시나리오별 표
3. 새 기법 평균 − 헝가리안의 차이와 CI
4. 학습 계산량
5. 이 문서와 다르게 한 점

**판정.** 시나리오 9개, 날짜 3개라 표본이 작다.
- "헝가리안보다 낫다"고 말하려면 새 기법 평균(r0–r2) − 헝가리안의 95% CI가 0보다 작아야 한다.
- CI가 0을 포함하면 "차이를 보이지 못했다"고 쓴다.
- r 하나만 CI가 0보다 작은 것은 근거가 아니다.

## 8. 알려진 한계 (새 기법 결과를 읽을 때도 똑같이 적용된다)

1. **한 번 실행의 흔들림이 크다.** 경량 시뮬레이터에서 이동 시간을 1%만 바꿔도 주문 리드가 표준편차 30초로 움직였다. 정책 순위도 자기 자신과 70%만 일치했다. 작은 시간 차이가 이후 배정 순서를 바꾸기 때문이다. Webots도 비슷할 것으로 보지만, 시나리오마다 1회만 돌려서 확인하지 못했다. 위 CI에는 이 흔들림이 시나리오 간 차이로만 들어 있다.
2. **경량 시뮬레이터로 정책을 판정하지 않는다.** 경량과 Webots의 평균값 오차는 5% 안팎이다. 하지만 정책 쌍 순위 일치는 50%이고, 헝가리안을 21초 나쁘게 본다(`docs/experiments_iri.md` 8.3절). 경량은 학습과 사전 선별에만 쓰고, 보고하는 비교는 Webots로만 한다. 경량으로 모델을 고를 때는 한 번 실행이 아니라 여러 번(예: 이동 속도를 ±1–2% 바꾼 실행) 평균을 쓰는 것을 권한다.
3. **시험 날짜가 3개다.** 시나리오 9개지만 같은 날짜의 세 시나리오는 서로 독립이 아니다.
4. **처리량은 정책을 가르지 못한다.** 가동률이 약 50%라 1시간 동안 들어온 일은 어느 정책이든 처리한다. 출고 차이가 ±1.5유닛이다. 이 조건에서 정책이 바꿀 수 있는 것은 처리 속도(리드)다. 처리량을 비교하려면 로봇 수를 줄이거나 주문을 압축한 별도 조건이 필요하며, 그 조건의 베이스라인은 아직 없다.
5. **Webots가 결정적인지 확인하지 않았다.** 같은 입력에서 같은 결과가 나오는지 모른다.
