# 경량 시뮬레이터 (`lib/lite_sim.py`)

Webots 없이 같은 창고를 빠르게 돌리는 시뮬레이터예요. **WES 학습(강화학습)과 많은 조건을 훑는 실험**에 써요. 결과 확인은 Webots에서 해요.

- 같은 `scenario.json`, 같은 WES 인터페이스(`on_event` / `decide`), 같은 이벤트와 결정을 써요. 그래서 여기서 만든 스케줄러는 **고치지 않고** Webots에서 돌아가요 (`WES_MODULE=wes_runner WES_SCHEDULER=<모듈>`).
- 같은 `summary.json` 항목을 써요. 로그 폴더 이름은 `..._lite`예요.
- 1시간 에피소드가 **약 1초**예요 (Webots는 약 8.5분). 처음 한 번은 거리 지도를 계산하느라 10~15초가 걸려요.

## 실행

```bash
cd webots
python lib/lite_sim.py --scheduler sched_verify --policy event --seeds 0 1 2
```

코드에서 (예: 강화학습 스케줄러):

```python
from lite_sim import LiteSim
from nav import GridMap
from wes_runner import WES

grid, fields = GridMap(cfg), {}          # 여러 에피소드가 같이 쓰면 거리 지도를 한 번만 계산
wes = WES(cfg, scheduler=my_scheduler, log_dir=tmp_dir)
summary = LiteSim(cfg, wes, grid=grid, fields=fields).run()
```

강화학습 정책은 `Scheduler` 클래스로 만들어요 (`plan(state)`가 결정을 돌려줌). 경량 시뮬과 Webots에서 같은 클래스를 써요.

## Webots와 같은 것, 다른 것

| | 같음 | 다름 |
|---|---|---|
| 환경 | 주문 웨이브, 입고 트럭과 컨베이어, 출고 트럭과 마감 | |
| 오류 | t=0의 초기 기록 오류(Ghost·Hidden·Swap), 적치 후 위치 기록 오류(`record_slip_p`) | 로봇이 상자를 실제로 다른 칸에 놓는 물리적 오적치는 두 엔진 모두 구현하지 않았어요. |
| 로봇 | 작업 단계(이동, 확인, 집기, 이동, 확인, 놓기)와 보고, 통행 우선순위 규칙 | 바퀴, 충돌 회피 없음. 이동 시간 = 경로 길이 ÷ 속도 + 2초 + 1초 × (출발할 때 움직이고 있는, 나보다 통행 우선순위가 높은 로봇 수) |
| 시간 | | 0.5초 단위 (Webots 32 ms). 로봇 단계는 정확한 시각에 끝남 |
| 인식 | | 라벨을 항상 읽음 (UNREADABLE 없음) |

모델링하지 않은 것: 로봇 놓기 오류(S1_PLACE_ERROR), 입고 판독 실패, 순찰 로봇의 선반 훑기. 모두 기본값이 꺼져 있어요.

## 보정 (Webots 결과와 비교)

아래 수치는 이전 상위 60개 SKU 입력에서 측정한 기록이다. 현재 전체 SKU·날짜별 100개 이하 주문 입력(v3)에 대한 보정·정책 순위 검증 결과로 인용하지 않는다.

이동 시간에 두 값을 더해요.
- `leg_s` 2초: 이동마다 드는 회전과 정렬 시간
- `yield_s` 1초: 출발할 때 움직이고 있는 로봇 중, 나보다 통행 우선순위가 높은 로봇 1대당 양보 시간. 우선순위는 Webots와 같은 규칙이에요 (`nav.traffic_priority`: `task` 또는 `id`).

Webots 실행 47개(속도 0.3·0.8 m/s, 로봇 4·8대, 순찰 7+1, 정책 none·event·periodic, 오류 1·4배, 스케줄러 3종, 모두 번호 우선 통행)에 맞춰 두 값을 함께 정했어요 (2026-11-16). 아래 표는 작업 우선 통행 실행 4개를 더한 51개로 검증한 값이에요 (경량 seed 5개 평균). 처음에는 이동마다 고정 5초를 썼는데, 로봇이 적은 조건에서 가동률을 크게 높게 봤어요.

| | 고정 5초 (이전) | 2초 + 양보당 1초 (지금) |
|---|---|---|
| 운반 가동률 평균 오차 | 2.5% | 2.2% |
| 운반 가동률 최대 오차 | 18.1% | 8.2% |
| 로봇 4대에서 가동률 편향 | +16% | +5% |
| 평균 주문 처리 시간 평균 오차 | 5.7% | 5.4% |

검증은 `python tools/validate_lite.py`로 다시 돌릴 수 있어요 (결과: `logs/lite_validation.md`). 정확도, 정책 간 순위 일치, 오류 지표를 Webots 실행과 비교해요.

**쓸 수 있는 범위 (검증 결과):**
- 처리량, 처리 시간, 가동률, 배정 방식 비교: 쓸 수 있어요. 조건 단위 순위 일치는 가동률 100%, 처리 시간 92%, 출하 86%예요. 다만 로봇 4대에서 배정 방식 간 처리 시간 차이를 Webots의 절반 정도로 작게 봐요.
- 확인 정책 비교(틀린 기록, SHORT_PICK, DESTINATION_OCCUPIED): 아직 조심해야 해요. 순위 일치가 57~82%이고, Webots 쪽도 seed 3개라 흔들림이 커서 판단하기 어려워요.

**오류 관련 수치(SHORT_PICK, DESTINATION_OCCUPIED, 틀린 기록)는 Webots와 1:1로 맞지 않을 수 있어요.** 초기 오류는 시나리오에 고정되지만, 정책과 엔진에 따라 작업 순서와 관찰 시각이 달라집니다. `record_slip_p`는 PUTAWAY·RELOCATE 완료 시 기록을 옆 칸에 남길지 결정하며, 같은 LPN·적치 회차에는 같은 추첨을 사용합니다. 완료한 작업 집합이 달라지면 실제 발생 건수도 달라질 수 있습니다. 오류 비교는 동일한 시나리오를 두 엔진에 넣고 정책의 상대 성능까지 확인해야 합니다.

물동량이나 로봇 수를 크게 바꾸면 Webots 실행과 다시 비교해서 `--leg-s`, `--yield-s`를 맞춰요.

## 배정 학습 비용 비교 (2026-11-20)

`tools/train_assign.py`로 비용 후보 10개를 같은 조건으로 학습해 비교했습니다. 학습 조건은 로봇 8대, CEM 15회, 학습 시나리오 03-09 시드 42~47입니다. 시험은 03-09 시드 48~50과 03-22(주문 20%) 시드 42~44, 오류 시드 100~104로 모두 30 에피소드입니다. 로그는 `logs/cost_variants/`, 가중치는 `models/cost_variants/`에 있습니다.

| 비용 | 전체 주문 처리 시간 (기존 463) | 기존 대비 (짝 비교) | 출하 (기존 120.9) | 마감 놓침 (기존 1.60) |
| --- | --- | --- | --- | --- |
| **mix** | **434** | **−29 (표준오차 4)** | 120.8 | 1.73 |
| tardy_unit | 440 | −23 | 120.4 | 1.87 |
| unit_missed | 442 | −21 | 120.6 | 1.83 |
| order_all_dist | 443 | −20 | 120.2 | 1.60 |
| order_all_missed | 445 | −18 | 120.0 | 1.70 |
| order_all | 446 | −17 | 119.6 | 1.77 |
| tardy | 446 | −18 | 120.4 | 1.73 |
| unit | 447 | −16 | 120.5 | 1.90 |

| old (예전 기본) | 489 | +26 | 123.1 | 2.40 |

- **선택:** `mix` = 0.5×전체 주문 + 0.5×박스 단위 처리 시간 + 300×마감 놓침. 이것을 기본 비용으로 정했고, 가중치를 `models/assign_weights.json`에 넣었습니다. 예전 가중치는 `models/cost_variants/legacy_4robots_old.json`에 있습니다.
- `mix`의 출하(−0.1)와 마감 놓침(+0.13) 차이는 표준오차(0.28, 0.13) 안이라 차이가 있다고 볼 수 없습니다. 미리 정한 조건 "기존보다 나쁘지 않을 것"을 엄격하게 적용하면 통과하는 후보는 없습니다.
- 날짜별 `mix` 결과(기존 대비)입니다.
  - 03-09: 전체 주문 −44초로 15개 중 15개가 개선됐습니다. 하지만 박스 단위 처리 시간과 출하는 같습니다. 즉 끝내는 주문의 순서가 달라졌을 뿐, 전체 처리량은 그대로입니다.
  - 03-22: 전체 주문 −15초(표준오차 7, 15개 중 11개 개선), 박스 단위 −6초(표준오차 4)입니다. 출하와 마감 놓침 차이는 잡음 범위 안입니다.
  - 다른 후보(tardy_unit, order_all)는 03-22에서 기존과 비슷하거나 조금 나빴습니다.
- 경량 시뮬 결과입니다. 앞선 Webots 확인에서 개선 폭이 경량 시뮬보다 2~3배 작았습니다.

## 후보 창 기본값 (2026-11-20)

`lib/sched_learned.py`의 후보 창 기본값을 `feasible`로 바꿨습니다. `feasible`은 WMS 기록 기준으로 지금 시작할 수 있는 작업 중 앞에서부터 30개(`MAX_TASKS`)를 고릅니다. 예전 기본값 `raw`는 대기열 앞 30개를 그대로 잘랐습니다. 그래서 03-22 전체(과부하)에서는 실행 불가능한 PICK이 창을 막아 출하가 약 15개 줄었습니다. `feasible`에서는 출하가 baseline과 같았습니다(`logs/mix_vs_baseline_v1`, 로봇 8대). 03-09와 03-22 절반에서는 두 창의 결과가 같았습니다.

- Webots와 `train_assign.py`(`ASSIGN_WINDOW`, 기본 `feasible`)도 이 기본값을 씁니다.
- `tools/run_research.py`의 `learned30`·`learned_all`·`heuristic`은 비교를 위해 `raw`를 직접 지정합니다.
