# 로봇 놓기 실패와 수정 작업 (설계)

브랜치 `none/error`, 2026-11-21.

## 목적

사람 개입이 없는 창고를 가정합니다. 오류는 로봇이 만들고, 수정도 로봇이 합니다. WES는 피킹, 운반, 적치뿐 아니라 **잘못 놓인 박스를 원래 칸으로 옮기는 수정 작업**도 로봇에게 배정해야 합니다. 이 배정이 연구의 결정 변수입니다.

오류 모델은 Dhanaraj et al. (ICRA 2023, "Contingency-Aware Task Assignment and Scheduling for Human-Robot Teams")의 로봇 실패 모델을 따릅니다.
- 시도마다 성공확률이 있습니다.
- 실패한 시도는 실패 시점까지의 시간을 씁니다(왜곡 정규분포).
- 실패는 복구할 수 없습니다.

논문은 복구를 사람이 맡습니다. 본 연구는 이를 로봇의 재시도와 인수로 바꿉니다(아래 처리 순서, 붙여주신 확장안).

## 목표, 범위 밖, 실패 기준

- **목표**
  - 놓기 실패, 재시도, 인수, 격리를 Webots와 경량 시뮬에 같은 의미로 넣습니다.
  - q를 바꿔 가며 baseline과 mix를 Webots에서 비교합니다.
- **범위 밖**
  - 조용한 오류(아무도 모르는 기록 불일치)는 다루지 않습니다.
  - 집기 실패, 운반 중 실패, 출고 레인 놓기 실패도 다루지 않습니다.
  - 사람 오류(S1 이동, S2 반출, S3 반품 적치)는 이 브랜치에서 모두 끕니다.
  - 새 오류에 맞춘 가중치 재학습은 이번 범위가 아닙니다.
- **실패 기준**(동작해도 실패로 봄)
  - 성공한 놓기의 시간과 결과가 바뀌어, 오류율 0에서 결과가 예전과 달라지면 실패입니다.
  - 같은 시드인데 두 엔진에서 실패가 일어나는 박스나 시도가 다르면 실패입니다(아래 "시드"에서 확인).

## 오류 모델 (정한 것)

| 항목 | 값 |
|---|---|
| 적용 범위 | **랙 칸에 놓을 때만**: PUTAWAY와 RELOCATE의 목적지. 출고 레인은 제외 |
| 실패하면 | 박스가 목표 칸 바로 옆의 빈 칸(같은 면 ±1)에 놓입니다. 옆 칸이 둘 다 차 있으면 실패가 일어나지 않습니다 (기존 `place_error_p`와 같음) |
| 처음 시도 성공확률 p | 0.95 |
| 같은 로봇 재시도 성공확률 q | **{0.5, 0.8, 0.95}로 민감도 분석** |
| 다른 로봇 인수 성공확률 r | 0.95 |
| 재시도 횟수 | 처음 시도 뒤 최대 2회 (같은 로봇이 모두 3번 시도) |
| 인수 횟수 | 1회. 인수한 로봇은 재시도하지 않습니다 |
| 시도 간 독립 | 가정합니다. 같은 로봇이 끝내 실패할 확률은 (1−p)(1−q)², 격리까지 갈 확률은 (1−p)(1−q)²(1−r)입니다 |

## 처리 순서

1. **놓기.** 로봇이 목표 칸에 박스를 놓습니다. 성공확률은 p(인수 작업이면 r)입니다.
2. **확인.** 놓은 뒤 항상 목표 칸을 봅니다(`look_s`, 1초). 성공하면 지금처럼 `TASK_COMPLETED`를 보냅니다. 성공한 놓기에 생기는 차이는 이 확인 1초뿐입니다.
3. **재시도.** 실패하면 같은 로봇이 옆 칸에서 박스를 다시 집어 목표 칸에 놓습니다(성공확률 q). 최대 2회 반복하고, 매번 확인합니다. WMS와 WES는 이 과정을 모릅니다. 로봇이 혼자 처리합니다.
4. **실패 보고.** 3번 모두 실패하면 로봇은 박스를 마지막에 떨어진 칸에 둔 채 `PLACE_FAILED`를 보내고 작업을 끝냅니다. 내용은 작업, 목표 칸, 실제 칸, 품목, 인수 실패 여부입니다.
5. **WMS 기록.** WMS는 박스를 실제 칸에 기록합니다. 로봇이 확인했으므로 "확인된 기록"입니다. 원래 작업은 완료로 처리하고 "잘못 놓임" 표시를 남깁니다. 그리고 **수정 작업**(RELOCATE, 출발 = 실제 칸, 목적지 = 목표 칸, 원인 `PLACE_FAILED`)을 만들고 목표 칸을 예약합니다. 목표 칸은 이 수정 작업을 위해 계속 예약해 둡니다.
6. **인수.** WES가 수정 작업을 다른 로봇에게 배정합니다. 누구를, 언제 보낼지가 연구 대상입니다. 원래 로봇에게 다시 주는 것도 막지 않습니다. 인수 로봇이 놓을 때 성공확률은 r입니다.
   - **수정은 반드시 합니다.** WES는 수정 작업을 취소하거나 건너뛸 수 없고, 목표 칸 예약도 유지됩니다(WMS가 수정 작업의 CANCEL을 거절). 기록은 이미 맞게 고쳐졌지만 옮겨야 하는 이유가 있습니다. 박스가 떨어진 옆 칸은 다른 적치 작업이 쓰려던 칸일 수 있고, 저장 규칙(자주 나가는 품목은 출고 가까이)도 깨지기 때문입니다. WES의 결정은 "할지 말지"가 아니라 "언제, 누구에게 맡길지"입니다.
7. **격리.** 인수도 실패하면 로봇은 `PLACE_FAILED`(인수 실패)를 보냅니다. WMS는 박스가 떨어진 칸을 **격리**로 표시합니다. 격리된 박스는 집기 후보에서 빠지고 칸도 쓰지 않습니다. 그 박스가 필요한 주문은 결품이 됩니다. 목표 칸 예약은 풉니다.

## 시간 (Dhanaraj 실패 시점)

- 성공한 시도는 지금처럼 `act_s`(2초)가 걸립니다.
- 실패한 시도는 τ초가 걸립니다. τ는 왜곡 정규분포 Skew(μ = act_s/2, σ = act_s/4, α = 0)에서 뽑고 [0.1, act_s]로 자릅니다. 논문처럼 평균은 정상 시간의 절반으로 두었습니다. 논문이 σ와 α를 보고하지 않아서, σ는 정상 시간의 1/4로 두고 α = 0(대칭)으로 두었습니다. **이 값들은 제가 정한 것입니다.** α는 설정으로 바꿀 수 있게 둡니다.
- 재시도에는 옆 칸으로 다가가 집는 시간(`act_s`)과 다시 놓는 시간이 더 듭니다. 인수에는 인수 로봇의 이동 시간이 자연히 들어갑니다.

## 시드

성공 여부와 τ는 (시드, 박스 LPN, 그 박스의 놓기 순번, 시도 종류)로 정합니다(`unit(seed, ...)`). 그래서 WES 정책이나 엔진이 달라도 같은 박스의 같은 시도는 같은 결과가 나옵니다. 기존 `place_error_p`도 같은 방식입니다.

## 검증 (Webots)

- **오류율 0 확인:** p = q = r = 1에서 Webots 결과가 확인 1초 말고는 예전과 같아야 합니다.
- **비교 실험:** p = r = 0.95, q ∈ {0.5, 0.8, 0.95}에서 baseline과 mix를 비교합니다. 하루 물량은 03-09, 03-22 절반, 03-22 전체이고, 시드는 3001, 로봇은 8대입니다.
- 경량 시뮬은 먼저 걸러 보는 용도로만 씁니다.

## 검토한 방식

1. **집기 실패만:** 박스가 제자리에 있어서 위치 수정 작업이 생기지 않습니다. 연구 질문과 맞지 않아 뺐습니다.
2. **놓기 실패 (선택):** 수정 작업이 그대로 생기고, 기존 `place_error_p` 코드를 다시 씁니다.
3. **실패 시점에 따라 결과가 다름:** 논문과 가장 비슷합니다. 하지만 Webots에 "박스를 든 채 멈춘 로봇" 상태를 새로 만들어야 해서 비용이 큽니다.
