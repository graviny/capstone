- 동결 방법: `baseline`, `learned30`(배포 그대로), `learned_fw`(후보 창 수정, 재학습/튜닝 없음).
  `learned_fw`를 고른 이유는 A3–A5만이며 age/cap은 채택하지 않는다(A6–A7: 이득이 없고 트레이드오프).
- 새 시나리오(생성 seed 3001–3003): 03-09 full, 03-22 full(과부하), 03-22 order-sample 0.5(중간~고부하) 각 3개.
  fault seed 300–304(이전과 겹치지 않음). 운반 4대. 오류 모델 marked-poisson-v1 mixed.
- 사전 판정 규칙(결과를 보기 전):
  1. `learned_fw` 출하량이 `learned30`보다 과부하 시나리오 3개 모두에서 paired CI가 0보다 크게 나오면
     "후보 창 수정이 붕괴를 해소한다"고 쓴다.
  2. `learned_fw` vs `baseline`의 완료주문 평균 처리시간·출하·미완료·불일치 지표를 시나리오별로 모두 표시.
     어느 한 시나리오에서라도 CI가 0을 포함하거나 방향이 반대이면 해당 부하에서는 개선을 주장하지 않는다.
  3. 시나리오 3개를 독립 표본으로 합쳐 p-value/CI를 만들지 않는다(n=3).
- 이 확인 실험이 끝나면 이 시나리오도 개발 세트로 편입된다. 최종 시험은 별도 신규 시나리오가 필요하다.

   가치 기반을 비교. 위험 점수의 calibration(Brier)을 먼저 보고. 배정 × 확인 2×2.
3. **ETA**: 보정/검증 로그 분리. 현재 A9는 1회 실행.

## H. 확인(VERIFY) 위치 선택 실험 (실행 전 기록)

**구현** (`lib/sched_verify.py`, `VERIFY_TICK_RULE`): 60 s마다 한 슬롯을 확인하는 tick 예산은 모든 규칙에서 같고
**어느 슬롯인가**만 다르다. 이벤트 기반 확인(SHORT_PICK 이웃, DESTINATION_OCCUPIED)은 모두 그대로 켜 둔다(`both`).
후보 = 기록상 점유된 랙 슬롯(비어 있다고 기록된 슬롯은 후보가 아니므로 S3/비기록 입고 위치는 tick이 직접 겨냥하지 못함).
- `sweep`: 기존 고정 공간 순회. `random`: 후보 중 균등 무작위(정책 자체 RNG, 외생 오류와 무관).
- `oldest`: 마지막 확인/기록 갱신 후 경과시간 최대(cycle-count 대조군).
- `value`: p·(1 + min(해당 SKU의 대기 PICK 수, 2)) 최대. p = 1 − exp(−λ·경과시간), 하나의 슬롯 위험률 λ는
  `online`(Gamma(0.5, 3600·N_점유) 사전 + 지금까지 발견한 불일치 수; **미탐지 오류는 세지 못해 과소추정**)
  또는 `config`(시나리오의 S1+S2 시간당 발생률/점유 슬롯 수, **기준용이며 배치 불가능한 사전지식**).
  가중치 1과 상한 2는 근거 있는 값이 아니라 가설이다(수요항의 기여는 `oldest` 대비로만 해석).
  비용 항(확인 이동시간)은 예산이 고정이라 순위에 영향이 없어 아직 넣지 않았다. 예산 자체를 정하는 단계에서 필요.
- 보정(calibration): 각 tick 확인 시점의 p와 결과(관측 ≠ 기록)를 `summary.wes_stats.verify_calibration`에 저장.
  선택 편향 때문에 Brier/reliability는 **`random` 규칙 run에서만** 위험 모델의 보정으로 해석한다.

**설계**: 배정 baseline(가장 가까운 유휴 로봇) 고정, 운반 4대, 시나리오 03-09 full·03-22 half 각 seed 4001–4003(=6),
fault seed 500–504, 오류 강도 ×1과 ×3(S1/S2/S3 모두 비율 배수), 방법 6개:
event(tick 없음)=`baseline`, `baseline@both-{sweep,random,oldest,value,value-config}`. 총 360 + 360회.
신규 fault seed이나 시나리오는 이미 쓴 것이다(독립 최종 시험이 아님).

**주 지표**: `settled_mismatch_mean`(낮을수록 좋음). 보조: 교정 시간, 확인 완료 수(예산 일치 확인), 출하, 평균 처리시간.
**판정(사전)**: value가 random·oldest보다 낫다는 문장은 해당 부하·강도에서 시나리오 3/3의 paired CI가 모두 같은 방향으로 0을
제외할 때만 쓴다. 확인 수가 방법 간 10% 이상 다르면 예산 일치 비교로 보지 않는다. 서비스 지표가 악화되면 함께 표시한다.

### H-1. 무효 run과 공통 수정 (`logs/verify_v1_x1`·`x3`는 기록용 보존, 분석 제외)
x1 180회 중 4회 `invalid`(모두 value/value-config 규칙, 같은 `SLOT_RESERVED` 거부). F-1과 같은 버그가 **baseline의
`sched_standin.plan`에도** 있었다(같은 스텝에서 PUTAWAY가 예약한 슬롯에 VERIFY 전송). value 규칙은 슬롯을 더 자주 고르는 탓에
노출이 더 컸음 → 방법별로 불공평한 노출이므로 `sched_standin`에도 동일 수정 후 `verify_v2_x1`·`x3` 재실행.
이 수정은 baseline 계열을 포함한 모든 방법에 공통 적용이며 이전 suite(수정 전) 결과와는 합산하지 않는다.

## I. 확인 위치 선택 결과 (`logs/verify_v2_x1`·`x3`, 각 180회 전부 complete, `code_unchanged=true`; 분석 `tools/analyze_verify.py`)

배정 baseline 고정, 운반 4대, 새 fault seed 500–504, 시나리오 6개. `settled_mismatch_mean`(낮을수록 좋음).

1. **주기 확인(tick)을 넣으면 이벤트 확인만(`baseline`)보다 불일치가 줄어든다**(x1 03-09: 약 6.9 → 5.4~6.3, x3: 14.1 → 11.4~14.2).
   당연한 결과이며 서비스 지표(처리시간 +0~+60 s)와의 교환이 있다. 시나리오별로 크기가 다르므로 개별 값을 본다.
2. **가설 기각: `value`(오류확률 × 대기 PICK 수요)는 `random`보다 나쁘지 않지만 낫지도 않다**(03-09 x1: +0.49/+0.76/+0.07, CI 대부분 0 포함),
   **`oldest`(관측 후 경과시간 최대)보다 03-09 x1에서 3/3 나쁘다**(+0.84/+1.22/+0.80, CI가 0 제외). half x1은 2/3, x3은 방향 혼재.
   → "수요를 반영한 위험 점수가 확인 가치를 개선한다"는 주장은 **이 데이터에서 지지되지 않는다.** 논문 기여로 쓰지 않는다.
3. 예산 일치 문제: value는 확인 수가 `random` 대비 0.80~0.93배로 적다(수요가 큰 슬롯이 이미 예약/관측 중이라 tick이 소모되는 것으로 추정, 미검증).
   `oldest`는 half x1에서 `random` 대비 1.14~1.17배. 따라서 value 열세의 일부는 예산 차이 때문일 수 있고, oldest 우세도 부분적으로 혼입돼 있다.
   10% 이상 차이가 나는 셀은 "예산 일치 비교"로 쓰지 않는다(사전 규칙).
4. `oldest` vs `random`: x1 03-09에서 3/3 음수(−0.35/−0.45/−0.73)이나 CI가 모두 0 포함. half x1 s4001만 CI가 0 제외. **일관된 우위를 주장할 수 없다.**
5. `value`와 `value-config`가 거의 동일한 이유: p는 경과시간에 단조 증가하므로 λ 값은 순위(argmax)에 영향이 없다(수학적 결과). 위험률 추정의
   정확성은 순위가 아니라 "확인 예산을 쓸지 말지"를 정하는 임계에만 의미가 있는데, 이번 설계(고정 예산)에서는 쓰지 않았다.
6. **보정(calibration)**: `random` 확인에서 online 위험 모델은 평균 p가 관측 불일치율보다 낮다(03-09 x1: 0.044 vs 0.0625;
   03-22 x3: 0.071 vs 0.191, 미탐지 오류를 세지 못하는 설계상 과소추정과 일치). Brier는 상수 기준율 예측과 거의 같다
   (0.0597 vs 0.0586, 0.0422 vs 0.0429, 0.1071 vs 0.1067, 0.1669 vs 0.1546): **경과시간 기반 위험 모델은 상수 확률보다 정보가 없다.**
   즉 "경과시간이 위험을 예측한다"는 가정 자체가 이 오류 모델에서 확인되지 않는다. 오류가 Poisson(시간 균일, 슬롯 균일)로 발생하도록 합성했기 때문에
   경과시간이 정보를 줄 이유가 약하다(슬롯 균일 선택 → 어느 슬롯이나 같은 확률). 구조(공간 군집/SKU별 위험)가 있는 오류 모델에서만 의미가 생길 수 있으며
   이는 실제 데이터 없이 임의로 만들어 유리하게 만들면 안 된다.
7. 서비스 비용: tick 확인은 x1 03-22 half에서 평균 처리시간 +20~+90 s를 만들었다(`flow`). 정확도–서비스 교환을 같이 보고해야 한다.

**결론**: 이 단계에서 "가치 기반 확인"은 신규 기여로 성립하지 않았다. 남는 사실은 (a) 주기 확인이 이벤트 확인만보다 기록 정확도를 높이고
서비스 비용을 만든다, (b) 합성 균일 오류 모델에서 경과시간·수요 기반 순위는 무작위를 일관되게 이기지 못한다. 다음 연구 질문은 오류 모델의 현실성
(공간·SKU 군집 오류를 지지하는 실데이터/문헌)과 예산 결정(확인 횟수 자체를 정하는 문제)이다.

## J. 부하 적응형 배정 `adapt_fw` (실행 전 기록)

**동기(G절)**: 한 가중치가 모든 부하를 지배하지 못한다. 배포 가중치(age<0)는 비포화, 재학습 가중치(age>0)는 포화·중간에서 baseline 수준 이상.
**방법**: WMS가 보여 주는 대기 작업 수/로봇 수를 지수평활(시정수 300 s)해 임계 τ=3.5 이상이면 재학습 가중치, 미만이면 배포 가중치.
후보 창은 `feasible`. 새 학습 없음, 두 가중치는 이미 있던 것.
**τ의 근거(결과 비참조)**: baseline 개발 run(`confirm_assign_v1`, seed 3001–3003)의 로봇당 대기 작업 평균 = 03-09: 2.4–2.5,
03-22 half: 4.6–5.0, 03-22 full: 12.0–12.3. 두 인접 부하 구간 평균의 중점 3.5를 선택했다. 성능을 보고 τ·시정수를 바꾸지 않는다(이번 실험 안에서).
대기 작업은 재고 없는 백오더 PICK을 포함하므로 "로봇이 처리할 수 있는 부하"의 직접 척도가 아니라 이 시나리오군에서의 근사이다.
**평가**: 처음 쓰는 시나리오 seed 6001–6003 × {03-09 full, 03-22 full, 03-22 half}, fault seed 600–604, 운반 4대,
방법 baseline / learned_fw / retrain0_fw / adapt_fw. 주 지표: 완료주문 평균 처리시간 + 출하 + 미완료 + 불일치(함께 표시).
**판정(사전)**: `adapt_fw`가 "baseline보다 나쁘지 않다"고 쓰려면 9개 시나리오 전체에서 처리시간 paired CI 상한이 baseline 대비 양의 방향으로
유의하게 넘지 않아야 하고(악화 CI 제외), "더 낫다"는 해당 부하 3/3에서 CI가 0 제외일 때만. 둘 중 최고(learned_fw/retrain0_fw)와의 차이도 표시.
하나라도 반대면 그 부하에서 주장하지 않는다. 이 평가 후 이 시나리오는 개발 세트가 된다.
