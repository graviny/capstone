# 순찰 로봇 필요성 실험

질문: **로봇 총 수가 같을 때, 1대를 순찰 로봇으로 쓰는 것이 모두 운반 로봇으로 쓰는 것보다 나은가?**

## 1. 설계

순찰 로봇은 누군가 확인(VERIFY) 작업을 만들어야 일을 해요. 그래서 구성마다 **같은 확인 정책**을 넣고, 확인을 **누가** 하는지만 바꿔요.

| 요인 | 값 | 설명 |
|---|---|---|
| 로봇 구성 | `8+0`, `7+1` (운반+순찰) | 기본 레이아웃의 대기 위치는 운반 8, 순찰 3 |
| 확인 정책 | `none`, `event`, `periodic` (+ `both`) | 아래 표 |
| 오류 배율 | 1, 2, 4 | `gen_world.py --fault-scale`. 오류는 사람 원인만 (S1 이동, S2 반출, S3 반품 적치) |
| seed | 0~4 | 같은 seed면 주문, 입고, 작업자 오류 시각이 같음 |
| 시간 | 3600 s | `--duration` |

| 정책 | 내용 |
|---|---|
| `none` | 지금 임시 스케줄러 그대로. 예외는 우회만 하고 확인은 안 함 |
| `event` | SHORT_PICK·ITEM_MISMATCH가 나면 같은 면의 옆 칸(±3칸, 작업자가 옮기는 최대 거리)을 확인. 목적지가 차 있는데 라벨을 못 읽었으면 그 칸을 확인 |
| `periodic` | 60초마다 가장 오래 확인 안 한 선반 칸 하나를 확인 (정기 재고 조사) |

확인은 순찰 로봇이 있으면 가장 가까운 쉬는 순찰 로봇이, 없으면 가장 가까운 쉬는 운반 로봇이 해요. PICK이 우선순위가 더 높아서 운반 로봇은 피킹이 없을 때 확인해요. 정책이 동시에 열어 두는 확인 작업은 4개까지예요. 최근 120초 안에 본 칸은 다시 확인하지 않아요.

이 정책은 **실험용 임시 정책**(`lib/sched_verify.py`)이에요. 팀의 Baseline/Proposed WES가 아니에요. 배정, 우회 규칙은 `sched_standin`과 같아요.

## 2. 실행

```bash
cd webots
python tools/run_patrol_experiment.py --dry-run          # 실행할 목록만 보기
python tools/run_patrol_experiment.py                    # 전체 (2 x 3 x 3 x 5 = 90회)
python tools/run_patrol_experiment.py --mixes 8+0 7+1 --policies none event periodic \
       --fault-scales 1 4 --seeds 0 1 2                  # 1단계 (36회)
python tools/summarize_patrol.py                         # 결과 표
```

- 실행은 하나씩 순서대로 해요. 월드 파일이 하나라서요. 이미 `summary.json`이 있는 실행은 건너뛰어서, 중간에 멈춰도 이어서 돌릴 수 있어요.
- 끝나면 기본 월드를 다시 만들어 둬요. 실행 중에는 `worlds/warehouse.wbt`와 `scenario.json`이 바뀌어요.
- **소요 시간:** 10분 실행 하나에 실제 3~5분이 걸렸어요. 1시간 실행 하나는 약 20~30분이에요. 전체 90회는 30~45시간, 1단계 36회는 12~18시간이에요.
- Webots 위치가 다르면 `--webots` 옵션이나 `WEBOTS_EXE` 환경 변수로 지정해요.

로그 폴더 이름: `logs/2023-03-09_wms-verify-<정책>_seed<n>_faults_pt_t<운반>p<순찰>_<정책>_f<배율>_d<시간>_batch`

## 3. 지표

`summary.json`에서 읽어요. `record_quality`와 `robot_roles`는 이 실험을 위해 supervisor에 추가했어요.

| 분류 | 지표 | 의미 |
|---|---|---|
| 처리량 | 출하 수, 완료 주문, 마감 놓침, 평균 주문 처리 시간 | 운반 로봇 1대를 뺀 비용이 여기에 보여요 |
| 오류 영향 | SHORT_PICK+ITEM_MISMATCH, DESTINATION_OCCUPIED | 로봇이 틀린 기록 때문에 헛걸음한 횟수 |
| 기록 품질 | `settled_mismatch_mean` | 틀린 기록 칸 수의 시간 평균. 로봇이 작업 중인 칸은 빼요 (완료 보고 전까지 잠깐 다를 뿐이라서) |
| | `mean_time_to_correct_s` | 틀린 기록이 정정되기까지 걸린 평균 시간 (10초 간격 측정) |
| | `open_at_end` | 끝날 때까지 정정되지 않은 칸 수 |
| 로봇 | 운반·순찰 가동률, 총 이동 거리, 진단 | 진단은 정체(ROBOT_STUCK) 등 |

`timeseries.csv`에도 10초마다 `record_mismatch_settled` 열이 추가됐어요.

## 4. 결과 읽는 법

`summarize_patrol.py`는 두 표를 만들어요 (`logs/patrol_experiment_summary.md`).

1. 구성 × 정책 × 오류 배율별 평균 (표준편차)
2. **짝지은 차이:** 같은 정책·배율·seed에서 `7+1` − `8+0`. seed마다 주문과 오류가 같아서 이 차이가 가장 공정한 비교예요.

| 결과 | 해석 |
|---|---|
| 같은 정책에서 7+1의 출하 차이 ≥ 0 | 순찰 로봇이 필요하다는 강한 근거 |
| 출하는 조금 줄지만 틀린 기록·SHORT_PICK이 크게 줄어듦 | 트레이드오프. "처리량 x% 대신 틀린 기록 y% 감소"로 제시 |
| 오류 배율이 커질수록 7+1이 따라잡음 | 교차점이 "순찰이 필요한 오류 수준" |
| 모든 조건에서 8+0이 나음 | 운반 로봇이 확인을 겸하는 게 낫다. 이것도 의미 있는 결과 |

`none` 정책은 기준점이에요. 7+1에서 순찰 로봇이 놀기 때문에 "로봇 1대를 버린 비용"을 보여 줘요.

## 5. 첫 확인 실행 (600 s, event, 오류 2배, seed 0)

| | 8+0 | 7+1 |
|---|---|---|
| 출하 | 21 | 22 |
| SHORT_PICK | 0 | 1 |
| VERIFY 완료 | 0 | 2 |
| 틀린 기록 시간 평균 | 1.82 | 1.03 |
| 끝날 때 미정정 | 6 | 2 |
| 운반 가동률 | 0.94 | 0.95 |
| 순찰 가동률 | - | 0.07 |

10분짜리 한 번이라 결론을 낼 수 없어요. 파이프라인이 동작하는지만 확인한 결과예요. 운반 로봇 가동률이 95% 근처라서 **운반이 병목**이에요. 이런 상태에서는 운반 1대를 빼는 비용이 커요.

## 5-1. 1단계 결과 (3600 s, 오류 1·4배, seed 0~2, 36회)

전체 표는 `logs/patrol_experiment_summary.md`에 있어요. 아래는 같은 seed끼리 짝지은 **7+1 − 8+0** 차이의 평균이에요.

| 오류 배율 | 정책 | 출하 | 틀린 기록 시간 평균 (낮을수록 좋음) | 끝날 때 미정정 (낮을수록 좋음) |
|---|---|---|---|---|
| 1 | none | −4.0 | +0.75 | +1.7 |
| 1 | event | −3.3 | +1.08 | +4.0 |
| 1 | periodic | −2.7 | **−0.51** | **−2.3** |
| 4 | none | −4.0 | +1.14 | +4.3 |
| 4 | event | −1.0 | −0.17 | +1.0 |
| 4 | periodic | −5.0 | +3.24 | +5.3 |

- **출하:** 모든 조건에서 8+0이 1~5개 더 많아요. 오류 1배에서 8+0은 풀린 133개를 모두 출하했어요(상한). 그래서 실제 차이는 이보다 클 수 있어요.
- **기록 품질:** 7+1이 확실히 나은 조건은 오류 1배 + periodic 하나뿐이에요. 오류 4배 + periodic에서는 오히려 8+0이 나아요. 운반 로봇이 많으면 평소 작업으로 들르는 칸도 많아서 그만큼 기록이 고쳐지기 때문으로 보여요.
- **운반 로봇에 여유가 있어요:** 1시간 평균 운반 가동률은 74~87%예요. 8+0에서 운반 로봇이 확인 작업을 7+1의 순찰 로봇만큼, 또는 더 많이 해냈어요 (event, 4배: 59 대 46건).
- **순찰 로봇은 놀아요:** 순찰 가동률은 7~38%예요. periodic은 60초에 1건으로 제한돼 있어서 순찰 로봇이 더 일할 수 없었어요.
- 마감 놓침은 7+1이 조금 적어요. 하지만 출하가 적어 대기 중인 박스가 적은 영향일 수 있어서, 7+1이 낫다는 근거로 보기 어려워요.
- seed 3개라 표준편차가 커요 (출하 1.5~3.5). 차이가 작은 칸은 잡음일 수 있어요.

**잠정 결론:** 이 조건(고정 정책, 운반에 여유 있음, 쉬는 순찰 로봇은 놂)에서는 **순찰 로봇을 두는 이득이 보이지 않아요.** 운반 로봇이 남는 시간에 확인을 해내기 때문이에요.

**다음에 볼 것 (2단계 후보):**
1. 7+1 + `--patrol-sweep`: 쉬는 순찰 로봇이 선반을 훑게 해서 순찰 로봇을 끝까지 써요.
2. 물동량을 늘려(`--inbound-scale` 등) 운반에 여유가 없는 조건을 만들어요. 순찰 로봇이 의미 있을 수 있는 조건이에요.
3. periodic 간격 줄이기(예: 20초). 확인을 더 많이 할 때 누가 하는 게 나은지 봐요.

## 6. 한계

- 오류 원인은 사람만이고, 입고 판독 실패는 꺼져 있어요 (spec.md 12절).
- S3에서 로봇이 라벨을 읽으면 기록이 바로 그 품목으로 바뀌어요. 그래서 S3는 확인 없이도 대부분 정정돼요.
- `event` 정책은 S1으로 옮겨진 박스를 옆 칸에서 찾아요. S2(반출)는 찾을 박스가 없어요.
- 정책 이름이 같아도, 로봇이 다르면 S3 발생 여부가 조금 달라질 수 있어요 (작업 ID와 목적지로 정해짐).
